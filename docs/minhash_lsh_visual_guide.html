Stage 1: k-Shingling (Turning Text into Sets)

Exact string matching fails when texts differ by a single character, whitespace, or variable name. k-Shingling maps a linear sequence of tokens into a set of overlapping n-grams ($k=3$ words in this example):

Document A (Original Code)

def add(a, b):
    return a + b

Word Shingles ($k=3$):

("def", "add", "a") ("add", "a", "b") ("a", "b", "return") ("b", "return", "a") ("return", "a", "+") ("a", "+", "b")

Document B (Added Comment)

def add(a, b):
    return a + b # sum

Word Shingles ($k=3$):

("def", "add", "a") ("add", "a", "b") ("a", "b", "return") ("b", "return", "a") ("return", "a", "+") ("a", "+", "b") ("+", "b", "#") ("b", "#", "sum")

Stage 2: The 128 Hash Functions & What "Minimum" Means

Storing thousands of shingles per document is too heavy. We compress each document into a fixed-size vector of 128 integers.

Question: Are there 128 different algorithms?

No! We use Universal Hashing. A single formula creates 128 unique random hash functions by choosing 128 pairs of random numbers $(a_i, b_i)$:

h_i(x) = (a_i * x + b_i) mod p     [where p = 2,147,483,647 (giant prime)]

Question: What does "Minimum" mean? (Concrete Walkthrough)

Suppose Document A has 3 shingles base-hashed to integers: {10, 45, 80}.
Let’s compute Slot 1 and Slot 2 of Document A's signature using $p = 101$:

Slot 1: Using h_1(x) = (3x + 7) mod 101

Shingle x Formula (3x + 7) Result mod 101 Comparison
10 (3 * 10) + 7 = 37 37 ★ MINIMUM (37)
45 (3 * 45) + 7 = 142 41 41 > 37
80 (3 * 80) + 7 = 247 45 45 > 37

➔ Slot 1 of Document A's signature is 37!

Slot 2: Using h_2(x) = (5x + 13) mod 101

Shingle x Formula (5x + 13) Result mod 101 Comparison
10 (5 * 10) + 13 = 63 63 63 > 9
45 (5 * 45) + 13 = 238 36 36 > 9
80 (5 * 80) + 13 = 413 9 ★ MINIMUM (9)

➔ Slot 2 of Document A's signature is 9!

Document A MinHash Signature: s_A = [37, 9, s_3, s_4, ..., s_128]

Why Minimum? Taking the minimum hash is mathematically identical to drawing a random shingle from the document! If two documents share 75% shingles, their minimum hashes match 75% of the time!

Stage 3: LSH Banding & Buckets (Avoiding 500 Billion Comparisons)

Comparing all pairs of 1,000,000 documents requires 500 Billion comparisons! LSH Banding cuts the 128-number signature into 16 bands of 8 numbers each ($16 \times 8 = 128$):

# LSH Bucketing in Python: buckets = [{} for _ in range(16)] # 16 dictionary tables for doc_id, sig in enumerate(all_signatures): for band_idx in range(16): # 8-integer tuple acts as dictionary key band_key = tuple(sig[band_idx * 8 : (band_idx + 1) * 8]) if band_key not in buckets[band_idx]: buckets[band_idx][band_key] = [] buckets[band_idx][band_key].append(doc_id)

Scaling to 1 Trillion Documents: Bands vs. Buckets Mathematics

Crucial Clarification: 16 Bands ≠ 16 Buckets!

A common misconception is thinking there are only 16 buckets. In reality:
• We have 16 Bands (16 separate hash tables).
• Inside each band, there are billions of possible buckets!

Each bucket key is an 8-integer tuple: (s_1, s_2, s_3, s_4, s_5, s_6, s_7, s_8). Since each integer is 64-bit, the number of possible bucket keys is $(2^{64})^8 \approx \mathbf{10^{154}}$ (virtually infinite!).

Probability of 2 unrelated documents accidentally matching an 8-integer band key:
P(Accidental Collision) ≈ ( 1 / 2^64 )^8 ≈ 10^(-154) [Mathematically Impossible!]

This means unrelated documents NEVER land in the same bucket. A bucket only receives multiple documents if their text is genuinely identical or near-duplicate!

What does each bucket look like across 1 Trillion Documents?

In web-scale training data (Common Crawl / GitHub), bucket occupancy follows a heavy-tail Power-Law Distribution:

Bucket Occupancy % of Total Buckets What's Inside? Compute & Algorithm Action
Exactly 1 Document ~85% – 90% Original, unique text, novel code, unique articles. Zero Comparisons! Automatically ignored.
2 to 50 Documents ~9% – 14% Real duplicates: syndicated news, blog reposts, forked repos. Verified in RAM via 128-integer signature check.
> 1,000 Documents < 0.1% Monolithic boilerplate: MIT/Apache licenses, cookie notices. Super-Bucket Cap: Collapsed in O(1) time without pairwise checks.

The Grand Takeaway: You do NOT compare millions of documents against each other. 90% of your documents sit alone in their private bucket and are never touched. You only spend compute on the ~10% of buckets with multiple colliding items!

Stage 4: Your Scenario — Candidate Pairs & Cluster Pruning

Here is what happens when:
• Band 1 bucket has: [Doc 1, Doc 10]
• Band 16 bucket has: [Doc 1, Doc 99]

Doc 1 Doc 10

➔ Candidate Pair: (Doc 1, Doc 10)

Band 16 Bucket #8271
Key: (82, 4, 19, 71, 33, 15, 6, 90)
Doc 1 Doc 99

➔ Candidate Pair: (Doc 1, Doc 99)

Step 4A: How do we compare them? (Do we compare shingles?)

No! Comparing shingles or loading text from disk is too slow. Instead, we compare the full 128-number MinHash signatures in CPU RAM:

def compare_signatures(sig_a, sig_b): # Count how many of the 128 integers match exactly matching_slots = sum(1 for a, b in zip(sig_a, sig_b) if a == b) return matching_slots / 128.0 sim_1_10 = compare_signatures(sig_1, sig_10) # Result: 108/128 = 0.844 (>= 0.80 -> MATCH!) sim_1_99 = compare_signatures(sig_1, sig_99) # Result: 105/128 = 0.820 (>= 0.80 -> MATCH!)

Step 4B: What if both match? (The Graph Cluster Resolution)

Doc 1 matches Doc 10, AND Doc 1 matches Doc 99. They form an Undirected Graph Cluster:

The Pruning Action:
1. Connected components merges `{Doc 1, Doc 10, Doc 99}` into one cluster.
2. We pick Doc 1 (the highest quality representative) to keep in the dataset.
3. We delete Doc 10 and Doc 99 completely from the pretraining corpus!
